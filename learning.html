Chapter 1: The Internet Fundamentals (Baby Steps)

1. What is "Hosting"?

The Layman Analogy: When you invite friends to a Diwali party, you are the host. You provide the house, lights, food, and chairs.

In computer language, hosting means putting your project files inside a computer that never sleeps, never disconnects from Wi-Fi, and is always ready to serve visitors 24 hours a day, 7 days a week. When our files were only on your Windows laptop, your project had no host—the moment your laptop went to sleep, the website disappeared. On Google Cloud, Google is our host.

2. What is a "Server"?

A server is literally just a computer. It has CPU, RAM, and a hard drive just like your laptop. The only difference is that it has no monitor, keyboard, or mouse attached. It sits in a high-tech cooling room inside a data center, listening to internet cables, ready to serve web pages to anyone who asks.

3. What is a "Browser"?

Chrome, Edge, Safari, Brave. A browser is simply a digital television screen. If a server sent you raw computer code, it would look like messy text. The browser takes that raw code and paints beautiful buttons, colored badges, images, and tables on your screen.

4. What is "HTTP" (The Rules of the Phone Call)?

When you call a restaurant to order pizza, you speak polite, standard words ("Can I get a pizza?"). HTTP (HyperText Transfer Protocol) is that standard polite language computers use to talk over digital cables.

  • HTTP GET: "Please GET me this page so I can look at it." (Sent when you click a link or open the dashboard).
  • HTTP POST: "Here is the form I just filled out; please POST (save) it into your database." (Sent when you submit a new student or membership).
  • HTTP 200 OK: The server's thumbs-up meaning "Everything worked perfectly, here is your page."
  • HTTP 404: "Sorry, that page does not exist."
  • HTTP 500: "Oops, my internal Python code crashed."

5. IP Address vs. URL (Phone Number vs. Contact Name)

  • IP Address: Every computer connected to the internet gets a numerical phone number (e.g., 34.93.241.228).
  • URL (Website Link): Humans cannot remember dozens of 10-digit numbers! A URL (like google.com or our Cloud Run URL) is just the contact name in the internet's contact book (called DNS). When you type the URL, DNS automatically dials the IP address for you.

Chapter 2: Why Use Google Cloud Platform (GCP)?

The Big Question: What would happen if we didn't use Google Cloud?

If you tried hosting this website from your personal laptop on your desk:

  • No Public IP (NAT Wall): Home Wi-Fi routers hide laptops behind Network Address Translation (NAT). People outside your house cannot connect to your laptop.
  • Zero Reliability: If your laptop battery dies, Windows reboots for updates, or home Wi-Fi drops, the entire college club system crashes.
  • Hacking Vulnerability: Opening your home router ports invites malicious port scanners directly into your private home network.

The Restaurant Analogy (The 4 Main Actors)

Every professional cloud web application works like a restaurant:

  1. The Customer (The User / Browser): A student or interviewer clicks buttons on their phone.
  2. The Waiter (Google Cloud Run / Python Flask): Welcomes the customer, takes the order, and runs the application logic.
  3. The Locked Filing Cabinet (Google Cloud SQL / MySQL): The heavy, permanent storage room in the back. Stores 69 students, 5 clubs, events, and memberships. Only the waiter is allowed inside.
  4. The Bank Vault / Safe (Google Secret Manager): Holds the secret keys and database passwords. The waiter shows an official security badge to grab the key only when unlocking the cabinet.

Chapter 3: Relational Database Essentials (MySQL 8.0)

1. Why not just use a Microsoft Excel Sheet?

  • Concurrence & Corruption: If two club heads edit an Excel sheet simultaneously, one overwrites the other. Relational databases use ACID transactions to guarantee zero conflicts.
  • Typos & Integrity: In Excel, someone can type "comp eng" and another "Computer Engineering", or assign the same PRN to two students. Relational databases strictly enforce data rules.

2. Relational Design: Primary Keys & Foreign Keys

Keys Simplified

Primary Key: Your college PRN or Aadhar card number. Uniquely pinpoints one human being. It cannot be duplicated or blank (student_id in the Students table).

Foreign Key: Writing your friend's PRN on an event entry pass. In the Memberships table, student_id and club_id are foreign keys linking the student to the club without duplicating the student's full name, email, or department.

Chapter 4: The 3 Database Superpowers

1. Database View: ClubSummary (The Saved Lens)

Instead of forcing Python to write long, messy SQL queries joining 3 tables every time someone loads the dashboard, we created a View. It acts like a saved lens that automatically displays the club name, faculty coordinator, and active member count in one simple command: SELECT * FROM ClubSummary;.

2. Database Trigger: trg_increase_member_count (The Automatic Turnstile)

Like a turnstile counter at a metro station that clicks +1 whenever a passenger enters. In our database, an AFTER INSERT trigger automatically runs UPDATE Clubs SET member_count = member_count + 1. Python code doesn't do the math—the database guarantees its own accuracy automatically.

3. Stored Procedure & Cursor: sp_audit_club_counts (The Robot Inspector)

A Stored Procedure is a saved mini-program stored directly inside MySQL. Our procedure uses a CURSOR (like a robot finger pointing down a list) to inspect each club one by one, count the actual rows in Memberships, compare it against Clubs.member_count, and report or automatically heal discrepancies (p_fix = 1).

Chapter 5: Docker & Containerization

1. The "It Works on My Machine" Nightmare

A developer writes code on Windows. When they send it to a Linux server, it crashes because of missing packages, different Python versions, or wrong file paths.

2. The Shipping Container Revolution

Before standard shipping containers, loose cargo broke on wooden ships. Standard steel containers seal everything inside and fit on any ship or train worldwide. Docker is that steel container for software. It seals Python 3.13, Flask, all libraries, and our code into a standard unit.

Image vs. Container (Classic Interview Question)

Docker Image: The Recipe in a cookbook (the static, frozen blueprint on disk).

Docker Container: The Baked Cake on your table (the live program running in memory).

Chapter 6: Google Cloud Run & Cloud SQL

1. Google Cloud Run (Serverless Compute)

  • Serverless: You don't manage virtual machines or operating system patches. Google automatically provides CPU and RAM when users arrive.
  • Scale-to-Zero (min-instances=0): When zero students are using the site at night, Google turns off the container. You pay ₹0.00 while idle.
  • Budget Ceiling (max-instances=2): Even under high traffic, Cloud Run will never launch more than 2 instances, mathematically preventing unexpected billing.

2. Why Cloud SQL is Kept Separate from the Container

Critical Concept: Ephemeral vs. Persistent

Containers in Cloud Run are ephemeral (temporary). Every time you redeploy or the app sleeps, the container is destroyed and replaced with a fresh one. If your database lived inside the container, all your student records would be permanently deleted on every restart! That is why the database lives on dedicated, durable SSD storage in Google Cloud SQL.

3. The Private Underground Tunnel: Unix Domain Sockets

Rookie student projects open their database port to the entire internet (0.0.0.0/0), allowing hackers to attack it. Our architecture leaves Cloud SQL with zero public access. Cloud Run and Cloud SQL communicate across a private Unix Domain Socket (/cloudsql/project-...:club-mysql-instance) inside Google's private Mumbai data center backbone.

Chapter 7: Cloud Security & Secret Manager

1. The Rookie Mistake: Passwords in GitHub

Hardcoding passwords in code or committing .env files to GitHub leads to bots stealing credentials in under 60 seconds.

2. Google Secret Manager & The Principle of Least Privilege

  • Secret Manager: An encrypted vault. The password string (club-db-password) is injected into Cloud Run memory at runtime.
  • IAM Service Account (club-app-sa): A robot security badge given to our app. Following the Principle of Least Privilege, it has only two permissions:
    1. roles/cloudsql.client: Permission to connect to the database.
    2. roles/secretmanager.secretAccessor: Permission to read only the password.
    It cannot create servers, cannot view billing, and cannot alter projects.
  • Parameterized Queries: All SQL queries use %s tuple substitutions (e.g. cursor.execute("SELECT * FROM Students WHERE student_id = %s;", (student_id,))), making SQL Injection mathematically impossible.
